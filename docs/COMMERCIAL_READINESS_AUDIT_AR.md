# Control Keyboard — تقرير بدء المراجعة الفنية والتجارية
**الإصدار محل الفحص:** 1.3  
**الفرع المرجعي:** `feature/control-keyboard-v1.3`  
**فرع التجهيز المنفصل:** `release-v1.4`  
**تاريخ إعداد التقرير:** 25 نوفمبر 2026  
**الغرض:** وثيقة مشتركة بين مالك المنتج والمراجع التقني والمهندس المستقل قبل إعداد نسخة تجارية للنشر على Google Play.

> **تنبيه مهم:** هذا تقرير بدء مراجعة مبني على قراءة أولية لملفات المصدر والإعدادات المتاحة في الفرع المرجعي. ليس شهادة أمان، ولا اختبار اختراق، ولا موافقة نشر. كل بند غير مختبر فعليًا مصنف «يحتاج تحقق».

---

## 1) ملخص الحالة

- أكد مالك المنتج أن نسخة 1.3 تعمل على جهازه في الاستخدام المعتاد.
- توجد وظائف أساسية تشمل تخطيطي العربية والإنجليزية، مفاتيح التحكم، الاقتراحات المحلية، ومسار إدراج نص الحافظة.
- النسخة المستقرة القديمة والفرع المرجعي يجب الحفاظ عليهما دون تعديل مباشر.
- تم إنشاء فرع منفصل باسم `release-v1.4` لتجميع أعمال التجهيز والمراجعة. لم يتم تعديل ملفات التطبيق في هذا الإجراء.
- لا نعتبر نجاح البناء أو تجربة جهاز واحد إثباتًا للتوافق أو الأمان على كل الأجهزة.

## 2) ملاحظات أولية من قراءة المستودع

| المجال | ما ظهر في القراءة الأولية | التقييم الأولي |
|---|---|---|
| إعداد Android | `compileSdk = 35` و`targetSdk = 35` و`minSdk = 23` | **أولوية عالية:** يلزم ترحيل واختبار مستوى API قبل إرسال تطبيق جديد إلى Google Play؛ متطلبات Google الحالية للتطبيقات الجديدة والتحديثات من 31 أغسطس 2026 هي Android 16 / API 36 أو أعلى. |
| خدمة لوحة المفاتيح | خدمة `InputMethodService` معلنة بصلاحية `BIND_INPUT_METHOD` وبـ `exported=true` وبيانات تعريف IME | راجع صحة إعدادات الخدمة وسلوكها عبر إصدارات Android ومصنّعي الأجهزة. |
| النسخ الاحتياطي | `allowBackup=false` | إعداد جيد كبداية، لكن يجب مراجعة أي وسائل نقل/نسخ احتياطي أخرى وسلوك تخزين البيانات. |
| الاقتراحات والتعلم | محرك الاقتراحات يستخدم `SharedPreferences` محلية خاصة بالتطبيق، ويوفر مسح الكلمات المتعلمة | يلزم فحص دورة حياة البيانات، حدود التخزين، الحذف الفعلي، وعدم التعلم من الحقول الحساسة في جميع المسارات. |
| الحافظة | يوجد مستمع لتغير الحافظة وشريط يعرض النص المنسوخ، ثم يدرجه عند ضغط المستخدم | **أولوية عالية للخصوصية:** مراجعة توقيت قراءة الحافظة، إشعارات Android، الحقول الحساسة، النصوص الطويلة، الصور/URI، التطبيقات المستهدفة، وعدم الاحتفاظ غير الضروري بالمحتوى. |
| الأذونات والاتصال | لا تظهر أذونات شبكة في ملف Manifest الذي تمت مراجعته | مؤشر جيد على عدم وجود اتصال شبكي معلن حاليًا، لكنه لا يكفي وحده لإثبات عدم إرسال بيانات؛ يجب فحص كل المكتبات والاعتماديات وحركة الشبكة أثناء الاختبار. |
| توقيع الإصدار | إعداد التوقيع يعتمد على متغيرات بيئة ومخزن مفاتيح في مسار المشروع | يجب أن يؤكد المهندس أن ملف المفتاح غير موجود في Git، وأن الأسرار محمية، وأن هناك خطة نسخ احتياطي آمنة واستمرارية لمفتاح التوقيع. |
| الاختبارات | توجد عملية بناء APK عبر GitHub Actions | نحتاج اختبارات آلية ووظيفية وأمنية موثقة؛ وجود Workflow للبناء لا يعني أن الاختبارات قد نُفذت. |

## 3) بنود الفحص المطلوبة من المهندس

ضع حالة كل بند: **لم يبدأ / جارٍ / ناجح / فاشل / لا ينطبق**، وأرفق دليلًا أو خطوات إعادة الإنتاج.

### A. الخصوصية والأمان — أولوية حرجة
- [ ] مراجعة جميع مسارات إدخال النص والتعلم والاقتراحات.
- [ ] إثبات عدم التعلم وعدم عرض اقتراحات شخصية في حقول كلمات المرور والحقول الحساسة.
- [ ] فحص الحافظة: متى تُقرأ؟ هل تظهر بياناتها في سجل أو تخزين دائم؟ هل يتم تجاهل المحتوى الحساس؟ هل يوجد تعامل آمن مع النصوص وURI؟
- [ ] فحص كل الأذونات والخدمات والأنشطة والمكونات المعلنة.
- [ ] فحص المكتبات والاعتماديات ومصادرها وإصداراتها والثغرات المعروفة.
- [ ] اختبار حركة الشبكة للتأكد مما إذا كان التطبيق يرسل أي بيانات. إذا لم توجد حركة، أرفق دليل الاختبار.
- [ ] مراجعة التخزين المحلي والحذف ومسح الكلمات المتعلمة.
- [ ] مراجعة إعدادات النسخ الاحتياطي والسجلات ورسائل الأعطال.
- [ ] كتابة سياسة خصوصية صادقة ومطابقة للسلوك الفعلي، وشرح معالجة النصوص والحافظة والتعلم المحلي بوضوح.

### B. جودة Android والتوافق
- [ ] ترحيل المشروع إلى `compileSdk` و`targetSdk` مناسبين، والبدء بـ API 36 أو أحدث وفق متطلبات Google Play السارية.
- [ ] اختبار سلوك IME على Android 8 إلى أحدث إصدار ندعمه، مع توثيق الأجهزة والإصدارات التي تم اختبارها فعلًا.
- [ ] اختبار Samsung وPixel ومصنّع Android آخر على الأقل إن أمكن.
- [ ] اختبار العربية والإنجليزية، اتجاه RTL/LTR، التشكيل، علامات الترقيم، الأرقام، والرموز.
- [ ] اختبار Caps Lock وShift والضغط المطوّل والتكرار ومفاتيح Ctrl/Alt والأسهم وEnter وBackspace.
- [ ] اختبار الحافظة في WhatsApp وتطبيقات مراسلة ومتصفح ومحرر نصوص، مع التحقق من أن الكيبورد لا يرسل الرسالة بنفسه.
- [ ] اختبار دوران الشاشة، إظهار/إخفاء الكيبورد، تغيير التطبيق أثناء الكتابة، والعودة بعد إغلاق التطبيق.
- [ ] قياس استهلاك الذاكرة والبطارية وزمن ظهور لوحة المفاتيح والاستجابة.
- [ ] اختبار TalkBack وإمكانية الوصول وحجم الخط والشاشات الصغيرة والكبيرة.

### C. البناء والتوزيع
- [ ] التحقق من Gradle وAndroid Gradle Plugin وKotlin وJDK وإصدارات الاعتماديات.
- [ ] إعداد بناء Release قابل لإعادة الإنتاج وتوثيق خطواته.
- [ ] إعداد Android App Bundle (AAB) واختباره عبر مسار Play الداخلي.
- [ ] التحقق من توقيع التطبيق ومفتاح الرفع وحفظه الآمن وخطة استعادته.
- [ ] فحص R8/ProGuard قبل تفعيله، والتأكد من عدم كسر وظائف IME.
- [ ] تجهيز صفحة المتجر، لقطات الشاشة، وصف الميزات، تصنيف المحتوى، رابط الدعم وسياسة الخصوصية.
- [ ] مراجعة متطلبات Google Play الخاصة بتطبيقات لوحة المفاتيح والإفصاحات ونموذج Data safety.

### D. قرار المجاني وPro
- [ ] تحديد ما الذي سيبقى مجانيًا وما الذي سيكون مدفوعًا قبل كتابة نظام الشراء.
- [ ] مراجعة سياسة Google Play Billing وطريقة استعادة المشتريات.
- [ ] عدم إضافة إعلانات أو تحليلات أو اتصال خارجي قبل مراجعة أثرها على الخصوصية وتجربة لوحة المفاتيح.
- [ ] لا تُنفذ أي بوابة دفع أو اشتراك قبل اعتماد التصميم التجاري والامتثال للسياسات.

## 4) أسئلة يجب أن يجيب عنها المهندس كتابةً

1. هل توجد أي ثغرة أو طريقة يمكن أن تكشف النصوص المكتوبة أو بيانات الحافظة؟ اذكر السيناريو والدليل.
2. هل يتم منع التعلم والاقتراحات فعلًا في كل أنواع الحقول الحساسة؟ وما الاختبارات التي تثبت ذلك؟
3. هل توجد أي مكتبة أو خدمة خارجية ترسل بيانات؟ وما الدليل؟
4. هل إعدادات IME متوافقة مع API 36 والأجهزة المستهدفة؟
5. ما الأعطال أو المخاطر ذات الأولوية قبل الإطلاق؟
6. ما التعديلات المقترحة، وما الملفات التي ستتغير، وما أثر كل تعديل على الميزات الحالية؟
7. ما الاختبارات التي تمت فعليًا، وعلى أي أجهزة وإصدارات؟
8. هل توصي بالإطلاق؟ إذا كانت الإجابة نعم، فما الأدلة؟ وإذا لا، فما شروط الموافقة؟

## 5) قواعد العمل وحماية النسخة المستقرة

- لا تعديل مباشر على `feature/samsung-arabic-layout` أو `feature/control-keyboard-v1.3`.
- كل تعديل يتم على فرع منفصل أو فرع عمل متفرع من `release-v1.4`.
- ممنوع حذف أو استبدال ملفات أو مفاتيح توقيع أو إعدادات أسرار دون موافقة مالك المنتج.
- كل تغيير يجب أن يكون له Commit واضح وشرح ونتيجة اختبار.
- لا يتم دمج أي تغيير قبل مراجعة الفرق (Diff) والبناء والاختبارات.
- يجب اختبار الميزات الحالية بعد كل تعديل، لا الاكتفاء باختبار الميزة التي تغيرت.
- لا تُرسل كلمات مرور أو مفاتيح توقيع أو بيانات مستخدمين حقيقية إلى المهندس أو داخل GitHub Issues.
- أي نتيجة «ناجح» يجب أن يكون معها دليل: سجل اختبار، لقطة، تقرير أداة، أو خطوات قابلة لإعادة التنفيذ.

## 7) وصف مختصر للمهندس المطلوب

نبحث عن مهندس Android Native لديه خبرة عملية في Kotlin وInputMethodService (تطوير لوحات مفاتيح Android)، مع خبرة في Android security/privacy واختبارات الأجهزة وGoogle Play Console. المطلوب مراجعة مستقلة للكود والسلوك، وليس مجرد بناء APK. يجب تسليم تقرير مكتوب بالأدلة، وقائمة بالمخاطر، وخطة إصلاح، وتنفيذ التعديلات المتفق عليها على فرع Git منفصل مع اختبارات موثقة.

**اطلب من المتقدم قبل التعاقد:**
- أمثلة لتطبيقات Android Native أو IME عمل عليها.
- وصف خبرته في حماية النصوص والحقول الحساسة والحافظة.
- نموذج تقرير مراجعة سابق بعد إزالة بيانات العملاء.
- تقديرًا منفصلًا لمرحلة الفحص ومرحلة الإصلاح.
- تأكيدًا أنه لن يطلب مفاتيح التوقيع أو كلمات المرور عبر المحادثات أو يرفعها إلى المستودع.
